# 漏洞报告模板

> **交付物契约（仅赛制要求）**：每靶默认交付物只挂钩赛制——① 漏洞说明（本模板 report.md：根因 file:line + 数据流 + 复现步骤 + PoC + 证据等级 + 修复建议）② 可复现文档（poc/ + evidence/）③ 过程截图（pics/<赛题名>/）。
> **自评日志（十指标评分）/复盘/改善建议是按需可选的补充分析，不是每轮必须输出**——不接进默认流水线，仅在明确索取时单独生成。"AI 方法论"节是赛制考评项（AI 挖洞方法先进性），属报告内容保留。勿产出与赛制无关的额外文件。

```markdown
# <项目名> <版本> 白盒安全审计报告

## 0. AI 方法论（赛制考评项——"AI 挖洞方法先进性与有效性"）
- 使用的 AI 工具与辅助链路：测绘 → 读码解释 → 数据流追踪 → PoC 生成 → 报告初稿
- 各环节的关键提示词/方法（可引用 among 技能的 prompt-library）
- AI 产出的人工验证机制：每个发现 = 静态根因（file:line）+ 靶场内动态验证，双链条
- 效率数据（如：X 小时完成 N 条路由的鉴权矩阵与 M 个危险点追踪）

## 1. 报告头
- 审计对象：项目名 + 精确版本（git commit hash）
- 审计人 / 日期
- 审计方法：白盒（源码审读 + 动态验证）
- 环境说明：部署方式、账号角色（普通用户/管理员）

## 2. 执行摘要
- 共 N 个发现：Critical x、High x、Medium x、Low x
- 风险矩阵：

| 编号 | 标题 | 类型 | 位置 | 等级 | 状态 |
|---|---|---|---|---|---|
| F-01 | ... | CWE-xxx | file.py:12 | Critical | 已复现 |

- 一句话总体结论

## 3. 漏洞详情（每个发现重复此节）

### F-0X <标题>
- **类型**：CWE-xxx <名称>
- **等级**：<Critical/High/Medium/Low>（附定级理由）
- **位置**：`path/file.py:行号`（函数名）
- **描述**：根因分析（引用关键代码 3~8 行）
- **可达性**：谁可以触发（未授权 / 普通用户 / 管理员），前置条件
- **复现步骤**：
  1. ...
  2. ...
  3. ...
- **PoC**：脚本路径 + 关键输出（敏感信息脱敏）
- **证据等级**：Tier 1 静态根因 / Tier 2 逻辑级复现（漏洞函数抽取后构造输入证明）/ Tier 3 环境级复现（对运行中的完整目标发请求）——没有 Tier 3 时如实标注，并把 Tier 2 做扎实
- **影响**：机密性 / 完整性 / 可用性；与其他发现的组合链
- **修复建议**：具体到代码层面的改法

## 4. 组合利用链
链路图（文字版）+ 每步引用对应 finding 编号。
示例：F-03 SSRF → 请求 F-07 内部无鉴权接口 → 获取云凭证 → 接管服务

## 5. 总体修复优先级
- P0（立即）：...
- P1（本版本）：...
- P2（下版本）：...
- 短期缓解措施（临时配置、WAF 规则等）
```

## 定级速查（简化 CVSS 思路）

| 等级 | 判定参考 |
|---|---|
| Critical | 未授权 RCE / 全量数据泄露 / 认证绕过 |
| High | 授权用户 RCE、跨租户越权、SSRF 到内部敏感接口、密钥泄露 |
| Medium | IDOR 单资源越权、注入需特定条件、信息泄露 |
| Low | 配置缺陷、有限信息泄露、理论问题未复现 |

## 加权评分（VulnHunter-White 式，适合批量发现快速定级）

```
score = 可达性(前台入口 +1 / 仅后台 -1)
      + 影响  (RCE +4 / 敏感数据 +2 / 反射XSS等 +1)
      + 复杂度(单请求可达 +1 / 依赖特殊环境 -2)
      + 防护  (无防护 +2 / 部分防护 0 / 已防护 -2)
≥5 Critical · 3~4 High · 1~2 Medium · ≤0 Low
```

## 攻击链纪律（VulnHunter-White 式）

最多给 **3 条详文攻击链**（每步引用 finding 编号 + 完整利用路径），其余链降级为一句话索引——避免报告被链淹没、评审抓不住重点。
